\section{Realization}

\subsection{Model Registry and Promotion}
Successful runs can be registered as named, versioned models. Each version carries
a lifecycle stage, Staging, Production, or Archived, which the user changes
from the interface. The tracking server remains the source of truth for the
registry; the platform mirrors and controls it through its own \gls{ui}.

\subsection{Deployment as an InferenceService}
Deploying a model reduces to creating a single declarative resource on the cluster.
The serving operator reconciles this resource into a running deployment, a service,
and an ingress, backed by a framework-specific model server that loads the model
artifact directly from the object store.

\begin{lstlisting}[language=Python,caption={Deployment is expressed declaratively; the operator does the rest.},label={lst:isvc}]
inference_service = {
    "apiVersion": "serving.kserve.io/v1beta1",
    "kind": "InferenceService",
    "metadata": {"name": name,
                 "annotations": {"serving.kserve.io/deploymentMode": "RawDeployment"}},
    "spec": {"predictor": {"sklearn": {"storageUri": model_artifact_uri}}},
}
\end{lstlisting}

\subsection{Prediction}
The backend forwards prediction requests to the model server through the cluster's
\gls{api}, which avoids needing a publicly-routable address for every model. The
interface provides a tester where the user submits sample inputs and sees the
returned predictions.
